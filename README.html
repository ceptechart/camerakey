01 — Setup

Installation, building & running

The easiest way to use this mod is by installing the pre-built binary. Drop the .jar into your NeoForge mods folder and every feature is available in-game right away.

1

Grab the pre-built binary. Download camerakey-1.0.0.jar.

Place the file into the mods folder of your NeoForge 1.21.1 installation.

2

-- or -- build it yourself. Advanced users can grab the source from the CameraKey repository.

Open a terminal in the source directory and run:

.\gradlew build

The compiled binary lands at build\libs\camerakey-x.x.x.jar and installs the same way as the pre-built version.

02 — Usage

Documentation & commands

The basic usage of this mod involves creating sequences and keyframes. A sequence is a collection of keyframes that, when played, will smoothly transition the camera through a set of predefined positions for a set duration. This makes creating cinematic camera shots a trivial process.

This mod was designed to fail gracefully. Any malformed command should produce an informative error and nothing more.

Sequence commands

/sequence create <name> <optional: interpolation mode>

Creates a sequence with the specified name and interpolation mode. The sequence is created with a single keyframe at your current position.

/sequence delete <name>

Deletes a sequence of the specified name.

/sequence list

Lists all currently saved sequences.

/sequence play <name> <optional: playback duration>

Begins playback for a specified sequence, for the specified duration.

/sequence stop

Stops all playback immediately.

Keyframe commands

/keyframe add <sequence> <optional: interpolation mode>

Adds a keyframe to a sequence from your current position and rotation. The optional interpolation mode overrides the sequence's default for this keyframe only.

/keyframe pop <sequence>

Removes the last keyframe from a sequence.

/keyframe delete <sequence> <keyframe index>

Removes a keyframe at the specified index. Indexing starts from 0, the first keyframe is index 0.

/keyframe set <sequence> <keyframe index> <optional: interpolation mode>

Replaces the keyframe at the specified index with a new keyframe from your current position and rotation. Indexing starts from 0, the first keyframe is index 0.

/keyframe list <sequence>

Lists every keyframe in a sequence, along with its details.

/keyframe goto <sequence> <keyframe index>

Instantly teleports you to the keyframe at the specified index. Indexing starts from 0, the first keyframe is index 0.

03 — Motion

Interpolation modes

Each sequence has a default interpolation mode, which individual keyframes can override. The mode controls how the camera moves between frames.

instant
Snaps directly between keyframes.
linear
Constant speed throughout.
quadratic
Subtle ease in and out.
cubic
Sharp ease in and out.
bounce
Elastic movement between frames.
04 — Settings

Config options

Configurable via Main Menu → Mods → Camera Key → Config.

Default Playback Length
default: 10.0

How long a sequence plays for when no duration is specified.

Enable Catmull-Rom Splines
default: ON

Whether position interpolation follows a smooth continuous curve between keyframes. Useful for fluid motion, but can occasionally cause unwanted overshoot or clipping.

Default Interpolation Mode
default: linear

The interpolation mode a new sequence uses when none is specified.

05 — Under the hood

Mod architecture

The codebase is split into a handful of packages, organized by related systems.

Under the hood, in short:

The mod is split into a few clearly seperated parts, each responsible for one job. One part handles saving and loading the camera sequences, so that your work stays even after reloading the world. Another handles the in-game commands you type, translating them into actions to manipulate the internal data. A third part handles actually moving the Camera during playback, using an invisible object to carry the camera through the sequence rather then moving your character directly. A last part handles the math for smoothing the motion, kept seperate so it can be swapped out or reused later. Keeping these systems seperate means any of them (save format, commands, playback, motion math) can be changed without having the rework the others.

\data

The data package contains records and classes related to the data structures and save system used by the mod. This is where interpolation modes, keyframes, and sequences are defined. I opted to use NeoForge’s native SavedData system, to save the sequences directly alongside the level. Not only did this allow persistence across reloads, but it also ties the saved data to the dimension/level. A different set of sequences can be created and played in the nether and the overworld, for example. This data is saved to .dat files within the save folder. For the overworld, the saved data file can be found at “data/camerakey_saved_sequences.dat” and can be transferred between worlds. One downside to this approach, however, is that the saved data files can not be manually read or edited outside of the game.

\cmds

The cmds package contains classes related to interfacing with the player via in game commands. This includes the CameraKeyCommands class which contains the logic and helper methods for creating, editing, and deleting sequences and keyframes, as well as the CommandRegistration class which registers the commands and calls static methods from the former class.

\playback

The playback package contains all the classes and client-side logic required for playing through the sequences. This includes network payloads for communicating across the logical server to the client (so that playback can be initiated via commands.) as well as the actual playback logic. The playback works by spawning a custom camera anchor entity based on the vanilla “Marker” entity. This anchor entity is then moved through the sequences, and the player’s camera is attached to it. I opted for this over physically moving the player to sidestep things like player collision, entity interaction, view effects, physics etc.. Though this does present issues with chunk-loading, as the player does not physically move and cannot load chunks.

\util

The util package is slim and contains only a helper class containing easing functions, as well functions required for calculating catmull-rom splines. It felt appropriate to separate these functions out as they are abstract enough to be used in different contexts.

other

The only other classes include the mod’s main classes (entrypoints) and the mod config. I placed a few things in the mod’s config that I could see easy justification in altering based on user/project requirements. (e.g. you might not always want to use catmull-rom splines for camera movement.)

06 — Process notes

AI usage

I came to Claude with a broad plan and used it to help dial in implementation details, then leaned on a local AI interface (Open WebUI + OpenRouter + DeepSeek V4 Flash) for basic scripting support. I came back to Claude for things like project structure and advanced debugging. Overall, AI substantially accelerated implementation and reduced the time required to explore potential solutions, though diagnosing complex bugs still required some traditional troubleshooting.

Claude was also used to create the formatting for this .html readme. Though textual content remains written by myself.

More Details

The areas where AI proved most valuable were implementing mathematical systems and exploring alternative implementation strategies. Features such as interpolation methods, easing functions, and Catmull-Rom spline interpolation were developed much more quickly with AI assistance. Claude was also useful for suggesting approaches that I had not initially considered. One example was the recommendation to create a dedicated camera anchor entity and attach the player's camera to it, whereas I might have spent time directly manipulating the player.

One bug that I couldn't get the AI to fix immediately was a stutter around certain camera rotations when transitioning through keyframes. I intuited it had something to do with rotation lerping through its looped range, as I had faced similar problems when developing games in the past. Though I couldn't pinpoint exactly where it was happening in this context. When I mentioned the stutter to Claude, it erroneously attributed the stutter to the linear motion paths (this AI conversation led to implementing the catmull-rom splines, which was a good idea in its own right.) I had to screen record the stutter, and go frame by frame to discover it was doing a really fast 360. Then with Claude's help I was able to develop a solution where all the keyframed angles were unwrapped in the same 0-360 range and saved to a table before the animation playback started.

Known Limitations

One large limitation, since my implementation keeps the player frozen in place, chunk loading becomes an issue when playing sequences that are far from the player. Playing sequences outside of the player's loaded chunks results in void and missing terrain. This may be able to be fixed with a custom chunk-loading system that runs alongside animation playback.

With more time, it may also be useful to engineer a better control system. Using commands is straightforward, but can be verbose when editing large sequences. Having a "currently editing" sequence, could alleviate this. Custom keybinds or a UI solution would work too.
